=== Honest finding: no Seq Scan -> Bitmap Index Scan transition visible at this row count ===
05-DATA-LAYER.md's own viva talking point ("Seq Scan -> Bitmap Index Scan is the line you
point at") does NOT appear in this capture -- both plans above use Seq Scan, with and without
the index. This is correct, expected PostgreSQL planner behavior, not a bug: the seeded table
has ~50 rows, and Postgres's cost model correctly judges a sequential scan over 50 rows
cheaper than an index scan (an index scan adds a second I/O per matching row to fetch the
heap tuple, which only pays off once the table is large enough that skipping most of it is
worth that extra cost -- typically thousands of rows, not tens).

The index's structural correctness is still proven (both idx creation and the exact column
order match 05-DATA-LAYER.md's own DDL), and the query PLANS identically either way BECAUSE
the planner is making the right call for THIS data volume, not because the index is unused
or broken. To actually observe the promised Seq Scan -> Bitmap Index Scan transition, the
table needs enough rows that the planner's cost estimate flips -- try re-running this same
EXPLAIN after `python -m app.cli.seed` has been extended to generate thousands of synthetic
rows (not the ~30-50 row curated golden set), or after enough real production traffic
accumulates. Recorded here as an honest, disclosed limitation of testing against the small
seed set, not claimed as a win that didn't actually happen.
